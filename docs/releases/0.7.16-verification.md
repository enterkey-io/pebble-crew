## Reply-rendering measurement

Compared production release 0.7.15-preview.1 with this candidate using the same
300 persisted messages, browser, dark mode, Pixel 7 viewport and 2x CPU throttle.
Ran five alternating baseline/candidate pairs per scenario, with all emitted text
asserted inside the measured interval. Every run had zero page errors and zero
failed bridge responses. Load averages were about 1.8–2.1 on ten available cores;
no other local browser suite ran concurrently. This is browser fixture work, not
provider/network timing or a physical Safari thermal measurement.

| Scenario/metric                                                            | Released median (range) | Candidate median (range) |
| -------------------------------------------------------------------------- | ----------------------- | ------------------------ |
| Reply only: 100 chunks / 4,000 characters, 20 ms source cadence; scripting | 629 ms (603–634)        | 149 ms (137–156)         |
| Same reply: observed completion interval                                   | 2,902 ms (2,897–2,911)  | 2,913 ms (2,910–2,919)   |
| Typing plus 20 reply chunks at 100 ms cadence; scripting                   | 237 ms (230–245)        | 97 ms (95–100)           |
| Same typing run: input-to-next-frame p95                                   | 15.9 ms (13.2–18.3)     | 17.1 ms (15.3–18.3)      |

Reply-only retained JS heap after forced GC was about 32.8 MiB released versus
24.9 MiB candidate, with 1,275 versus 877 listeners. These are scoped snapshots,
not total browser memory or proof of an unbounded leak being eliminated.

Separate profiled runs were excluded from the table. The released profile showed
React context propagation, repeated historical-control work and transcript follow
layout reads. The candidate isolates token updates, stabilizes the document context
and leaves closed reaction menus unmounted. Remaining sampled work includes
transcript-follow layout reads and garbage collection. Emission cadence and browser
poll/paint scheduling limit end-to-end completion, so lower scripting does not make
the generated reply arrive faster. Input-paint ranges overlap: no demonstrated
typing-latency improvement. Physical iPhone heat remains an owner-device check.

Reproduce with `test/chat-workspace/input-performance.spec.ts`: use
`PEBBLE_INPUT_MEASURE`, `PEBBLE_INPUT_BASELINE_URL`, `PEBBLE_INPUT_MOBILE=1`,
`PEBBLE_INPUT_STREAM=1`, `PEBBLE_INPUT_STREAM_CHUNKS` and
`PEBBLE_INPUT_STREAM_INTERVAL`; `PEBBLE_INPUT_OUTPUT` separates run artifacts.
Set `PEBBLE_INPUT_NO_TYPING=1` for reply-only work. Profiling requires a separate
run with `PEBBLE_INPUT_PROFILE=1`.

The owner app's served version and installed-PWA behavior must be checked after
its operator installs the published tag. Publishing alone does not update that host.
