## Product decisions

The installed product is a private workspace belonging to its installer. The app runs in the owner's infrastructure: Node with local SQLite by default, or an equivalent adapter in the owner's Cloudflare account. Hermes can run independently on a VPS, home server, container or other supported host. Olares is neither required nor privileged. The vendor holds no user content, credentials, endpoints or sessions. Owner-local account/configuration state is allowed. Browser-to-Hermes traffic carries conversations; the app server need not reach the private Hermes network.

One installer agent establishes the app, plugin, persistent storage, HTTPS route, issuer trust, supervision and verified compatibility, then returns a working URL and separately delivered one-use ownership credential. There is no developer/agent relay loop. A static preview remains a clearly labeled preview, not the launch deployment.

First use automatically identifies the existing primary agent from a persisted verified workspace binding, or an explicit operator/installer primary binding backed by installation evidence; otherwise it uses the uniquely verified native root/default as the standard-installation default. Native `is_default` proves root/default, not which named agent an owner subjectively considers primary. A named-only or intentionally nonstandard deployment therefore needs an explicit installer binding before first use, without presenting a normal orchestrator picker. Sticky CLI selection and gateway launch identity alone are insufficient evidence. Show that existing agent and ask only for its public handle; do not ask the owner to choose an orchestrator from a roster. The normal path has three steps: create the private administrator login, confirm the detected agent's handle and appearance, enter its chat. Connections are optional and available immediately afterward. Other existing agents can be enabled later.

## Detection without identity guesses

Native `profiles.list` marks the root profile `is_default:true`. In both pinned builds, `hermes_cli.profiles.list_profiles` constructs that row as `name:"default"` at the resolved Hermes root; named profiles are false. `active_profile` is sticky CLI selection, and `get_active_profile_name`/`current_profile_name` identify a launch or executing profile. These are different concepts. A named gateway launch alone does not designate primary. Without an explicit verified primary binding, it must discover root/default and verify routing; an intentionally named-primary installation requires the installer evidence described above.

The plugin must return a versioned detection receipt: stable installation binding, native build revision/capabilities, root/default opaque profile reference, launch profile reference, discovery coverage, evidence type, observed revision, and outcome. Root paths are verified locally by the plugin and not exposed as browser authority. A directory name, display title, roster order, arbitrary browser path, or launch profile is never a fallback primary selector.

Algorithm:

1. Verify the already enrolled installation trust and any persisted verified primary binding. An existing initialized workspace retains its root; an explicit operator primary binding must identify the same installation and exact existing profile with verified route and recorded provenance. Otherwise use the standard default-detection path below. Obtain a complete authoritative roster for that installation. An empty or filtered roster is not evidence that no primary exists.
2. On the standard default-detection path, require exactly one boolean `is_default:true` row, verify its native selector is `default`, verify its resolved native home is the native root, and verify the native route opens that same profile. The root can be a custom Docker home; do not assume `~/.hermes`. An explicit verified named-primary binding follows its own exact-profile route check instead of requiring a root profile as its target.
3. Bind to durable installation identity. af0 exposes `install_id` in `profiles.list`; 29112 does not. The plugin must persist an opaque installation UUID under the verified root for older builds and bind its enrollment to that UUID. Keep the plugin binding stable on upgrade; record native install ID as additional evidence rather than silently changing keys. Missing/unreadable identity, identity changed after restore, and duplicate identity on simultaneously connected cloned installations require repair/re-enrollment, not implicit rebinding.
4. Return `detected` only after identity and route checks. `ambiguous_default`, `missing_default`, `incomplete_discovery`, `installation_mismatch`, `unreachable`, `unsupported` and `permission_denied` remain distinct. No enrollment/model calls occur on failure. Offer Retry and a redacted installation diagnostic the same installer can repair. Only an exceptional explicit owner repair may resolve conflicting installation evidence; a regular agent picker must not mask it.
5. On initialization, revalidate detection receipt and native revision. Establish the detected/bound same profile as the sole initial orchestrator. If already initialized, return the existing receipt; never overwrite a later owner-directed root transfer during reconnect.

Installation ID is an authority binding, not a profile UUID. Native profile names can change. Persist plugin bot UUIDs mapped to installation + verified native profile selector and canonical identity. Reconcile documented rename evidence where available (af0 `previous_names`) and require explicit repair where unavailable or conflicting. Never attach a deleted-and-recreated directory to an old bot solely because its name matches.

## Handle, persona and native routing

For the detected native default agent, suggested text: **“By default, Hermes gives your primary bot the handle @hermes. Keep it, or change it here. You can also change it later in Settings.”** Default input is `hermes`. For an explicitly bound named-primary installation, show its verified existing handle instead; do not falsely label that profile @hermes or offer it another profile's reserved identity. A handle edit changes only the workspace identity directory. It never renames/moves/clones the profile or edits its display name, SOUL, memory, channels, model or history. The initial agent keeps its existing persona and receives the additional role of orchestrator.

Use lower-case ASCII handles, 1–32 characters, starting with a letter and followed by letters, digits, `_` or `-`. Strip a single leading `@`; do not silently transliterate. Reserve `everyone`, `all`, `system`, `owner`, and protocol/room tokens. Reserve `hermes` for the real default profile even when its public handle changes. Reject collisions against all discovered native identifiers, historical routing aliases and friendly aliases belonging to another profile, including disabled/unmanaged profiles. Allow a handle matching aliases of the same identity. Validate atomically with directory revision; case-insensitive collisions fail with a concrete explanation. Renames hold old public handles as tombstones until the owner explicitly releases them after pending references are resolved.

All mention selection, navigation, rooms, management tools and current-role context resolve a public handle to a stable bot ID and then a native target. Persist structured mention recipient IDs with message intent; never route historical messages by today's spelling. Render historical identity with its recorded handle and link to the current bot. Native DM attribution stays native: both builds hardcode default's routing handle as `hermes`; af0 additionally resolves friendly aliases, older 29112 does not. Exact native IDs take precedence over friendly aliases, and `hermes` has special default semantics. A public label alone cannot change native sender signatures.

Provide a typed, caller-bound plugin messaging adapter using stable recipient IDs and verified native delivery. Supply public/native identity mapping to every participating turn and map native sender IDs to public identity in the web view; preserve raw canonical history. Never string-rewrite arbitrary transcript text or silently translate quotations/code into mentions. If native room routing cannot accept the equivalent structured recipient or verified explicit native target, disable that custom-handle route until its adapter is proven. Teach agents to use the directory/adapter, not raw friendly names. Handle-edit launch acceptance requires correct outbound routing, incoming DM attribution and room mentions in both builds, including reused chats; a cosmetic-only custom handle is insufficient.

## Avatar and color during first use

The same primary-agent confirmation step includes a compact Animated shape / Photo choice, shape and color picker, and a local photo picker with a live preview. White is included in the shape palette. Keep an existing native appearance or offer a deterministic default; the owner may continue without making a new choice. Use the same controls later in Settings. A changed handle must not change the avatar seed. Shape, color, public handle and orchestrator responsibility remain separate from SOUL/personality and native profile identity.

The [avatar system plan](AVATAR_SYSTEM_PLAN.md) defines portable geometry/motion, low-load scheduling, reduced motion, native metadata import/projection and owner-Hermes persistence. An isolated [motion study](../apps/web/avatar-lab.html) demonstrates appearance and simulated activity; it does not save appearance or implement this onboarding step. Native integration is separate work with revision checks and preservation of existing image avatars and unknown metadata.

## First chat and welcome

Initialize through durable steps: identity bound → exact profile enrolled → canonical native Bot Chat resolved → management plugin/tool/skill readiness verified → role context available → ready. Preserve SOUL, memories, channels and all existing histories. Enable native Bot Mode with its verified native marker/session contract; never create a substitute bot or merge unrelated channel sessions. Narrow plugin configuration changes are recorded explicitly.

The final action reads “Open my workspace” and explains that it starts one short welcome from the existing agent. Registration/detection makes zero model calls. Persist an intent before submission and a native receipt afterward. If submission outcome is uncertain, reconcile canonical history before retry; do not produce a second welcome. If the provider is unavailable, show setup complete with a retryable welcome failure and allow the owner to fix model readiness. Never synthesize an assistant introduction.

The welcome context gives public/native identity mapping, orchestrator responsibility, current permissions, actual verified tools, bundled `bot-web:manage-team` location and one useful next action. It must not claim an unfinished tool exists, claim all prior channel history is in this chat, invent team members, or treat the welcome as authorization to create agents/connect services. Existing personality is authoritative; role is a separate responsibility.

## One service catalog

Use one searchable **Connections** page and a compact “Connect a service” action from chat/bot settings. Cards explain useful outcomes, provider, authentication method, existing account availability, compatible setup paths and readiness. Show “Already in Hermes” first, then a small useful catalog from the installed native manifests; search exposes the remainder. Keep raw transport/configuration details in an optional technical disclosure. Do not create decorative integrations that have no verified backend recipe.

A service can have several setup recipes: native built-in toolset, existing configured MCP, catalog MCP, or installed plugin. Deduplicate by explicit catalog identity/provenance, not a similar name. Distinguish:

- **Connection:** authorized account/server resource held by Hermes, with scope, credential reference and lifecycle.
- **Tool:** executable action exposed to a particular bot/session; selecting a service does not authorize every action it offers.
- **Skill:** instructions/workflow. Installing or reading one neither supplies credentials nor grants tools.
- **Plugin:** executable extension that may provide all three. New code and widened plugin updates require explicit review.

Flow: choose useful service → reuse an existing compatible connection or select setup method → show recipient bot and requested scopes/tools → authorize required installation/access → configure necessary fields → authenticate → test → attach/activate → show an honest usable state and offer a concrete first task. Default to the current bot, not all bots. Owners may skip connections entirely. Bot-initiated requests use the same flow as an owner-review card, never ask for secrets in chat.

| Setup method  | Owner experience                                                                        | Implementation boundary                                                                                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| OAuth         | “Sign in to Service,” scope/account review, provider consent, return to same setup card | Tokens, PKCE verifier, refresh and exchange stay on Hermes. Native dashboard HTTPS OAuth primitives exist; their safe reuse through the plugin is required and not implied by Desktop gateway support. |
| API key       | Reuse stored compatible grant or masked owner-only field with provider instructions     | Browser submits directly to Hermes over authenticated HTTPS; never to model/chat/app database/logs. Do not require keys for OAuth/no-auth services.                                                    |
| No auth       | Explain remote destination/data use, “Connect,” test discovery                          | No fake login. Anonymous quotas/failures remain visible.                                                                                                                                               |
| Local service | Explain host/application prerequisite and minimal local resource scope                  | Runs on Hermes host, not automatically on browser device. Missing app/session/platform is actionable; never claim browser can access the owner's desktop through a server-side plugin.                 |

Initial certification targets: one native no-auth catalog recipe (for example installed-build Context7), one supported OAuth recipe (for example Linear after web callback proof), one API-key fixture/provider recipe, and one local fixture. These are test targets, not claims of currently working live integrations. Catalog availability is build-specific: af0 has `n8n-official`, 29112 has `n8n`; never alias or migrate these automatically. GitHub hosted MCP must not be invented as a generic DCR/OAuth recipe; the pinned catalog explicitly explains its per-host OAuth app requirement and suggests existing skills instead.

## Reusing native capability surfaces

Both builds provide MCP catalog/list/add/test/OAuth and profile-scoped capability management in source. Generic RPC forwarding is insufficient: af0 `mcp.servers.set_api_key` writes HTTP Authorization/Bearer headers and can replace existing custom headers; catalog `mcp.servers.add` with a preset does not establish that local code bootstrap occurred. Recipe-specific adapters must preserve headers, validate the actual authentication scheme, and distinguish configuration from code installation. af0 has typed contracts and richer runtime/connector state. Reuse native profile configuration and token storage through restricted adapters, not a second MCP client/configuration store in the browser. Native `mcp.servers.status` on af0 is cached status and explicitly does not probe or authenticate. `mcp.servers.test` connects/lists/disconnects; it is not proof of permission to perform a specific external action. `tools.configure` can rebuild a live session; plugin Python tools/prompt sections can remain deferred to a new session even when MCP tools/skills activate now. Model runtime proof remains necessary.

Existing local connection import is a reference to the same installation/profile resource after owner review, not credential export. Scan only known native configuration locations with permission; do not recursively scan homes for secrets. Show redacted account/resource metadata and effective tools. Cross-profile reuse requires a supported credential-reference grant or a fresh scoped authorization; native MCP configuration copying alone may leave unresolved `${VAR}` references. Never copy the entire `.env`, `auth.json`, SOUL or channel tokens.

The af0 Desktop connections surface joins native local MCP/plugin entries with **hosted Nous Portal account connectors**. Its `tools/connectors/portal/client.py` calls `/api/v1/connectors/*` with Nous access tokens, and gateway availability is account/rollout gated. These hosted connectors are not a self-hosted backend we can silently reuse. The private product defaults to owner-Hermes/local or direct-provider paths; existing hosted connections may be displayed as externally managed and require explicit disclosure/choice before reuse. No vendor-operated broker is required. Do not present hosted entitlement as guaranteed.

## Authentication, policy and failure behavior

Use a maintained owner-authentication library behind identical Node/SQLite and Cloudflare contracts, selected after a compatibility/security spike. Bootstrap consumes a high-entropy, expiring installation credential atomically with admin creation. No first-visitor claim, public registration or default password. Cookie sessions are Secure/HttpOnly, CSRF-protected, rate-limited durably and recoverable through an owner-local command. New devices sign in normally. Sign-out/password change/revoke-device are real server operations.

App issues short-lived signed client tickets for its authenticated session; the plugin trusts an operator-enrolled fixed issuer key/audience/origin, never browser-supplied JWKS. Proposed default ticket TTL: 5 minutes with stream reauthentication/closure at expiry and renewal before expiry. Maximum disconnected-session revocation lag is therefore 5 minutes; ordinary logout also closes that browser's streams. This bound, including already-running requests, must pass tests before it is promised. Native execution already accepted may continue; logout is not Stop. Key rotation accepts a bounded overlap; removing trust immediately prevents new tickets for that issuer. App API does not proxy conversations or need Hermes network access.

Connection states are separate dimensions: saved configuration, authorization, discovery test, attachment and active runtime. Display “Saved — sign in needed,” “Authorized — tools unavailable,” “Ready for this bot,” or “Restart needed,” never one misleading green connected flag. Record target profile/session/config revision and check time. Expired credentials, consent denial, provider downtime, missing executable, scope mismatch, stale revision, profile mismatch and unsupported flow have distinct retry actions.

Every mutation is enforced by the plugin management service. Owner or authenticated bot principal, normalized exact spec, revisions, approved capabilities, expiration and idempotency key bind a proposal. Agents may propose but cannot approve themselves or elevate grants. New accounts, remote code, widened tools/scopes and plugin updates require new consent; read-only tool tags are hints, not enforcement proof. Existing profile capabilities remain intact during enrollment; any tightening requires an explicit reviewed change. Workspace policy does not turn shared-OS profiles with shell access into sandboxes.

OAuth cancellation keeps the prior working credential/config intact. Failures after successful auth retain authorized state and retry discovery without new consent. Revoking a bot attachment removes its future use and refreshes/invalidate sessions; disconnecting an account lists affected bots, disables their grants, then removes local credentials and attempts provider revocation when supported. Distinguish local removal from confirmed provider revocation. Do not delete shared credentials still referenced elsewhere. Retrying uncertain install/configuration operations reconciles receipts before doing work again.

## Teams and delegated management

Keep one root orchestrator; teams/sections organize the roster and a separate reporting tree requires every enabled bot to reach the root without cycles. A leader can have direct reports. Name, public handle, role title/description and SOUL are separate fields. Derive the root star overlay from the authoritative orchestrator selection; the avatar plan specifies appearance independently. Team metadata interoperates with native `hermes-bots` section fields through full namespace read/merge/CAS.

Implement the real `workspace_agents` plugin tool and bundled management skill through one shared service used by web calls. An owner-authorized bot can enable an existing agent or create a genuinely new native profile, edit role cards and attach approved capabilities. Caller derives from actual runtime profile/session; missing binding fails closed, never defaults to `default`. Creation uses explicit non-cloning flags and approved model grant; `ok:true` with `model_set:false` remains partial, not ready. New bots do not inherit creator privileges. Role context refreshes at each turn and via authoritative reads in long-lived chats, because native plugin system sections can freeze. Prove tool/skill load in selected-profile and native DM subprocesses.

Task dependencies are independent of reporting edges. Persist task ID, assignee, dependencies, expected result, state and reporting destination. A queued native DM is not completion. Dependent work waits for verified prerequisite results/approval. Use native task primitives only after contract proof; a durable plugin coordinator is additional implementation otherwise.

## Scope and launch boundary

No owner infrastructure changes, real profile edits, deployment, release, design generation or broad UI implementation are part of this research pass. No vendor cloud agent, mandatory hosted connector broker, generalized MCP JSON editor, multi-owner SaaS, automatic credential copying, avatar design, full OS isolation, or automatic execution ordering from an org chart is proposed. Unresolved protocol/runtime spikes and exact release gates are listed in the execution plan. An unavailable optional catalog entry can be disabled individually; missing owner auth, primary detection, native Bot Mode, safe handles, approved management, or durable reconnection blocks product launch.
