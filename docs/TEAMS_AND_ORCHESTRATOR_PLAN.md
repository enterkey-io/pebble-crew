## Intended first use

After the owner creates/signs into their private instance, discover **all** existing Hermes profiles, including the default agent and ordinary profiles with no Bot Mode marker. Automatically detect the primary existing agent for initial orchestration, show its identity, and offer its editable public @ handle. The [onboarding and connections plan](ONBOARDING_AND_CONNECTIONS_PLAN.md) defines detection evidence, ambiguous-install handling and Settings behavior. This supersedes the earlier first-run orchestrator picker; do not drop the owner into an empty roster or manufacture a replacement assistant.

Confirming the handle and choosing **Start** establishes that detected profile as the workspace orchestrator, enables/reuses its native Bot Chat, provisions the verified workspace plugin/tool/skill for that profile, confirms readiness and opens its chat. Preserve the existing SOUL, memory, skills, channels, model settings and canonical history. The orchestrator's role is an additional workspace responsibility, not a new personality. Any required plugin activation/configuration change must be explicit and narrow; do not call those bytes unchanged if activation actually edits them.

The first conversational response should come from that actual profile. Supply bounded onboarding context so it can introduce its existing identity, explain its public @ handle, its orchestrator role, the real available management features and the owner's next useful action. Do not insert a fabricated assistant message claiming continuity or capabilities. Native registration makes zero model calls. The owner's Start action can authorize one short welcome turn; persist a welcome intent/receipt so refresh, retries or interrupted setup do not replay it. Reconcile native history on an uncertain send rather than blindly resubmitting. Do not overwrite an existing Bot Chat or merge unrelated channel histories.

A failed provider/tool readiness check keeps setup in an actionable pending state. An unavailable welcome response must not make an otherwise completed setup invent a chat response. A future no-Hermes install requires its own guided prerequisite path; it is not a reason to silently host an agent on our infrastructure.

## Organization and source of truth

Maintain one workspace orchestrator for the first release. Store organization, policy, management requests and receipts **on the owner's Hermes host**, under the integration's private state directory. Do not depend on browser local storage, vendor infrastructure or the owner's web server reaching the home network.

- **Workspace:** stable ID, native installation ID, exactly one orchestrator bot ID after onboarding, policy and revision.
- **Team/section:** stable ID, label, sort order and optional parent ID for future nesting. Teams can be empty and survive restart; deleting one moves members to Unassigned rather than deleting agents. Begin with one primary team per bot, matching native section behavior.
- **Bot reference:** stable app bot ID, native installation/profile identity, public handle, aliases, selected/ready state, role card and reporting relationship. Use native previous-name information to reconcile an explicit rename; never identify bots by display label alone.
- **Role card:** role/title, owner-editable short description, responsibilities, handoff expectations, expected outputs and declared limits. Role-card instructions supplement SOUL; they do not replace personality or independently grant tools/privileges.
- **Reporting:** a single immediate `reports_to` bot ID for each non-orchestrator bot. Every chain must reach the workspace orchestrator. Reject self-reporting, cycles, missing/foreign parents and independent roots. A team folder is not a manager, a permission grant or a group-chat room.
- **Capabilities:** typed references to approved toolsets, skills and MCP connections, with source/version, requested/enabled/verified state and owner authorization. A child's capabilities never inherit all the creator's access implicitly.

Keep **name, @ handle, role and description separate**. Native `ui_meta['hermes-bots'].title` is used as a friendly display name and may affect native mention aliases; it is not a safe place to substitute an occupational title. A bot can remain “Captain” / `@captain` while its editable role is “Coordinator” and its description explains the job. An explicit approved role/description edit can project a concise routing description into the top-level native description. Importing an existing agent must not overwrite its existing description or rename it just to designate the orchestrator.

The integration's private transactional store is authoritative for the workspace graph, role cards, policy and operation receipts. Native profile metadata remains authoritative for native identity/title/description. Mirror team membership into the existing section fields for Desktop interoperability. Persist mirror/reconciliation status rather than claiming a native metadata write and private-store write are one transaction. Reconcile external edits using revisions; never silently overwrite a native Desktop edit. Global orchestrator selection must be one atomic workspace change, not independently editable `is_orchestrator` flags scattered across profiles.

API responses compute `is_orchestrator` from that single workspace selection. Tomorrow's UI uses it for the star overlay; it is not stored in or inferred from the avatar. Changing the orchestrator is an owner operation that validates the resulting whole reporting tree and preserves agents/history.

## Runtime roles, identity and order of operations

Every enrolled agent needs current context covering its public handle, native identity mapping, role, team, immediate manager, root orchestrator, relevant teammates, allowed management actions and the management-skill identifier. Keep SOUL unchanged. A static description, stored prompt section or skill sitting on disk is insufficient by itself.

Use a bounded per-turn plugin context provider backed by the workspace store, plus `workspace.describe` for authoritative details. On long-lived/resumed chats, verify a changed role/manager reaches the next turn without resetting history or waiting for compaction. A skill is guidance, not a security boundary. Runtime context must not claim a tool, model or attachment is ready before verification.

Hermes plugins are profile-scoped. Discovery scans the current home's `plugins` directory, and profile configuration controls activation. Installing the bridge in the launch/default home does not prove a named agent—or a separately spawned DM recipient—loads its model tool, context hook and skill. Provision the verified plugin code through supported Hermes discovery for each enrolled profile, enable it narrowly, and test direct chat, resumed chat and native teammate-delivery processes. Do not clone profile configuration to accomplish plugin installation.

Public handles are stable and unique within the workspace, independent of title. For example, `@captain` may map to the default native profile even though its legacy internal alias is `@hermes`; teach that mapping explicitly. Validate both public handles and native alias collisions. af0's native friendly aliases can be used when unambiguous; the older build needs an explicit adapter. Reserve system tokens and reject an ambiguous selection rather than guessing or silently renaming an existing agent.

Mention lookup, user navigation, room addressing and management calls must use that same identity directory. Resolve public mentions to stable bot references and then verified native profiles, not arbitrary strings chosen by a model. A mention is not permission to broadcast a private conversation; explicit recipient semantics must be preserved. Native messages can still carry a legacy internal alias, so display identity and routing identity need explicit handling rather than merely changing an avatar label.

A reporting tree alone does not enforce execution order. Keep task dependencies and ownership distinct: task ID, assigned agent, `depends_on`, state, expected result and reporting destination. Prefer a verified native task/kanban primitive if it satisfies this contract; otherwise a small durable plugin coordinator is additional work, not something the current group room driver guarantees. A native DM acknowledgement means queued, not task completed. Dependent work starts only after its required result/approval is confirmed. Subordinates report through their immediate manager; escalation and final owner reporting converge on the orchestrator. Avoid unconditional all-agent broadcasts and acknowledgement loops.

## Management operations and the actual bot tool

Expose the requested service operations through one implementation used by the web API and the model-facing Hermes plugin tool. Do not duplicate profile mutation logic in React, a skill and a tool handler.

| Operation                            | Contract                                                                                                                                                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent.enable`                       | Enroll the exact existing native profile and reuse/initialize its canonical Bot Chat; no cloning                                                                                                                 |
| `agent.create`                       | Create a genuinely new native profile from an approved persona/role specification; choose provider authorization, minimal capabilities, team and manager explicitly; verify readiness before saying it is usable |
| `agent.update`                       | Edit a typed role card and approved public metadata with expected native/workspace revisions; do not accept arbitrary SOUL/config fields through this operation                                                  |
| `agent.attach`                       | Add/remove approved capability references using explicit delta semantics; preserve unrelated existing settings, verify activation, and report requested/saved/authentication-needed/usable distinctly            |
| `workspace.initialize`               | Owner confirmation of the detected primary profile and public handle; native enrollment + verified plugin provisioning + canonical open + one-time welcome receipt                                               |
| `workspace.describe` / `agents.list` | Read current identity, role/team/reporting/capability state without exposing credentials, filesystem paths or all SOUL contents                                                                                  |
| `workspace.set_orchestrator`         | Owner-only root transfer; validate every reporting chain and invalidate stale contexts/requests                                                                                                                  |
| `teams.*`                            | Create/rename/move/reorder teams and memberships without moving profile directories or deleting agents                                                                                                           |
| `agent.requests.*`                   | Owner inspection/approval/denial and status of precisely bound management proposals                                                                                                                              |

The model tool can be named `workspace_agents` with typed actions `list`, `describe`, `enable`, `create`, `update`, `attach` and `request_status`. `agent.create` etc. remain service operation names. The current `agent.enable` RPC is **not already an LLM-callable tool**. Register a proper tool/schema through `ctx.register_tool`, with authenticated runtime caller identity, and a bundled read-only skill via `ctx.register_skill`.

All enrolled bots can be given the ability to request bot creation, not only the orchestrator. Start with owner approval for mutations; let the owner configure bounded standing grants for the orchestrator or other named bots. Each new bot gets explicit capabilities/reporting, not its creator's privileges. Creating new agents can be delegated; selecting the owner/root or granting more authority cannot be self-authorized by an agent.

## Approval, retries and partial operations

UI gating means a real backend authorization decision, not a hidden button. Derive the actor from the Hermes execution/profile/session context, never `actor_profile` in model-supplied arguments or an ambient helper that silently falls back to `default`. Bind the caller to the intended managed profile/session. Missing or mismatched context fails closed. The existing browser grant and new model-tool caller are separate principal types; a bot cannot call an owner approval endpoint.

A management proposal records the actor, exact normalized spec, target IDs, required privileges, existing revisions, limits, expiry and idempotency key. Its owner approval authorizes precisely that proposal, not whatever arguments the bot submits later. Apply-time checks repeat identity, revision, graph and privilege validation. Persist request/operation receipts so timeout, restart, repeated model calls and owner double-clicks do not create duplicate profiles, chats or attachments. Readiness and partial failure must be explicit and resumable; do not silently delete a profile or canonical chat after a multi-step error.

For attachment, begin with an owner-approved capability catalog. New remote skills, executable MCP servers and new credential grants need review beyond toggling an already-approved resource. Never allow `agent.attach` to become arbitrary shell execution, an unrestricted URL fetch/installation API or a way for a model to read/copy provider/MCP secrets. Native profile creation defaults can mirror broad `.env`/authentication state; pass restrictive flags and implement a verified provider-specific grant instead of copying everything. Check native `applied` fields and the actual effective capability set, especially where an empty list resets defaults.

The API's permissions govern this management service; ordinary Hermes profiles sharing the same OS account are not filesystem sandboxes. An agent retaining unrestricted terminal/file tools may modify profiles outside the service. Do not advertise an organizational chart or these API approvals as OS isolation. Stronger cross-agent isolation would require a separately designed runtime/permission boundary.

## First agent's bundled skill

Prepare `bot-web:manage-team`, loaded through the normal Hermes skill system once the corresponding tool exists and is verified in that profile. Its draft is [here](proposals/manage-team-skill.md); it is intentionally outside the installed plugin and must not be advertised as available today.

The first orchestrator's first runtime turn must know where to read the skill and that it can discover existing agents, propose new ones, assign roles and reporting, request attachments and report verified outcomes. Teach supported actions explicitly, but do not pre-load the whole organization's private transcripts or other agents' SOULs. Newly enrolled/created bots receive the same workspace contract appropriate to their own permissions.

## Work before UI implementation

1. Freeze the identity/team/role/reporting schemas and management request/result contract. Include configuration revisions, readiness states and idempotent recovery from the start.
2. Implement a private transactional workspace store and validate single-root reporting, handle collisions, native rename reconciliation and section mirroring. No permission comes from role prose or a folder name.
3. Implement one management service over native profile/configuration primitives with provider/capability preflight, exact approvals and safe partial-operation recovery. Keep it unexposed until owner authorization is real.
4. Register/provision the actual Hermes model tool, context hook and bundled skill per enrolled profile. Prove the first existing agent and a native DM recipient can see and invoke them with correct caller binding, including restart/resume and role changes after chat has already started.
5. Prove creation of a genuinely new agent with its own persona, approved working model, selected tools/skill/MCP, canonical chat and reporting destination. Separately prove a second authorized bot can request creation and cannot approve/elevate itself. Test configured versus actually usable capabilities.
6. Prove task/dependency/handoff semantics with a small native orchestrator → manager → specialist scenario, including duplicate messages, unavailable agents, stale role changes and restart recovery. Do not claim order-of-operations guarantees from a static role card.
7. Alongside the already-required owner-login/reconnect work, implement primary-agent detection → public-handle confirmation → orchestrator enrollment → open canonical chat → one-time real welcome. Only then build tomorrow's team sections, role editor, @ picker, management review and orchestrator star UI over those contracts.

Acceptance must verify unchanged existing SOUL/memories/channels, zero model calls during registration, actual selected persona in the explicitly started welcome, current-role context in reused chats, routing collisions/default aliases, one orchestrator, no cycles, no duplicate creation after an uncertain response, preserved native metadata, fail-closed authorization, profile-scoped plugin availability, and no vendor content/credential paths. UI appearance alone is not evidence of any of these behaviors.
